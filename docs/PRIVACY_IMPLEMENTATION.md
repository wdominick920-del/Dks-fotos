# Photo privacy and promotional choice implementation

> Current behaviour (12 November 2026): The notice has a short summary, three section links and native expandable secondary explanations. All substantive content and consent safeguards remain. The duplicate reference-entry form was removed; a known reference still prefills the main consent field. Draft handoffs now use standard email apps first with an optional Gmail link.

The website notice is version 2026-11-06. It was drafted from the owner's detailed requirements in chat. The referenced DKs_Photography_Photo_Privacy_and_Consent.pdf was not attached as an accessible file and was not present in the workspace; its wording could not be compared and no PDF download was invented. Supply the PDF for source reconciliation before treating this as a transcription of that document.

No direct consent submission service is configured. The form prepares email and WhatsApp drafts, offers copy and a text-file download, and says the owner receives the choice only after the client presses Send. The downloadable record is client controlled; it is not a claim of server storage. No feedback or consent records are written into public files or browser local storage. No automatic publication is implemented.

Keep received records in a private booking system or inbox. Verify that each choice can be linked to the relevant person, booking and photographs; verify an adult's legal authority where applicable. An anonymous form, self-declared name or unverified email alone is not sufficient permission to publish. Missing/unclear permission means no promotion. Ask-first requires separate recorded approval of specific photographs. Unchecked channels, client names and tagging are not authorised. Refusal does not change service or price. Changes and withdrawals need manual verification and handling; sending a draft does not automatically remove photographs.

The visible record contains the notice version/link, Johannesburg date, preparation timestamp, client name, booking reference or event date, explicit choice, all five channel decisions, restrictions, applicable permission end date, represented person, necessary child-authority information when applicable, and explicit acknowledgement. Client names in this record are private booking identifiers, not a licence to publish names. Changing input invalidates the previous draft and download. A refusal or ask-first choice removes hidden channel authorisations; switching back to self removes child fields from the record.

The notice does not invent a registered business address, legal entity number, information officer, fixed retention period, storage provider, encryption method or audited safeguard. The owner should confirm actual storage locations, access arrangements, retention rules and any required business disclosures. The current notice explains how clients can ask about these. The Information Regulator link is https://inforegulator.org.za/.

If a verified private submission service is added later, implement and test confirmation handling before displaying a received/saved message. Retain the exact versioned record privately, provide a client copy, and show confirmed success only after an authenticated service response. A successful API response is still not verification of the client's identity or authority. Never put API secrets or record exports into GitHub Pages. Existing enquiry/review endpoints remain blank; this release uses draft handoff only.
